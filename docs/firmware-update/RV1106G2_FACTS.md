## 2. What this means for the BuildAI Serial Utility (v0.7.0)

What the tool knows today (SU paths): the Loader is "0x110e on the RV1106 in Loader mode" (`src/firmware/UsbProbe.h:52-53`), download mode is any 0x2207 device that is not the ADB gadget (`UsbProbe.h:55` `isDownloadMode() { return vid == 0x2207 && pid != 0x0006; }`), the flash layout is the image's env.img or the board's `/proc/cmdline` remembered per serial (`src/firmware/FirmwareJob.cpp:980,1044-1069`, `src/app/AppSettings.h:169`), the image's chip tag is parsed from `SFI` and only displayed (`src/firmware/RockchipTool.h:64,72`), Loader mode writes `EXF` + `WL <offset/512> <size/512>` per partition + `RD` with no chip check and MASKROM mode writes the whole image with `UF` (`src/firmware/SocFlasher.h:59-62`, `RockchipTool.cpp:201-298`), protected partitions are idblock/uboot/env/meta (`src/firmware/FleetFlasher.cpp:343`), and a board's USB port is learned by the bus-address suffix of its instance id because the Node's gadget shows no USB serial string (`UsbProbe.h:21-26`, `UsbProbe.cpp:38-46`).

### D1. Loader PID 0x110c instead of 0x110e (row 32)

- Already works: detection and the whole Loader flow. `isDownloadMode()` accepts any 0x2207 PID other than 0x0006; the `LD` parser reads `Pid=` generically (`RockchipTool.cpp:61-75`), `Mode=Loader` is what U-Boot rockusb reports (bcdUSB 0x0201 is the "Loader" marker upgrade_tool uses: `f_rockusb.c:86-92`); `-s <LocationID>` addressing is PID-independent. The fleet rule "a board whose port shows another download-mode pid than its Loader mode's is never written" compares per board, so it holds on either board.
- Breaks: nothing functional. Comments and docs state 0x110e / "110E" (`UsbProbe.h:23,52`, `docs/DESIGN.md:471`); a mixed bench (Node + G2) is not told apart by the tool today.
- Change: board profile keyed on the Loader PID (0x110e = Node U-Boot, 0x110c = RV1106G U-Boot); print the PID in the status line; docs.
- First-board test (no write): one G2 alone on the bus, `upgrade_tool LD` (nothing), then `su-fw flash-soc --dry-run` (shows the plan only), then `adb reboot loader` by hand and `upgrade_tool LD` every second for 30 s: expect `Vid=0x2207,Pid=0x110c,LocationID=<n> Mode=Loader`. Device Manager should show `USB\VID_2207&PID_110C\6&...&0&<port>` (empty iSerial, row 32). Then `upgrade_tool -s <LocationID> RD` and wait for ADB. If no Loader appears within 30 s, the board is either in BootROM download (rbrom fallback, row 35/38) or unpowered (row 40, D7): a power cycle recovers it, nothing was written.

### D2. Chip tag 1106 instead of 110E (row 20)

- Already works: `SFI` parsing is key:value generic, so "Chip Tag:1106" is shown in the summary; the Loader path never runs a chip check; the MASKROM path (`UF`) should now **pass** upgrade_tool's chip check because the G2 Loader answers "1106" (row 32; inference, upgrade_tool is closed). The Node's "Check Chip Fail" workaround (`docs/DESIGN.md:471-473`, `docs/firmware-update/uboot-rockusb-chip-info.patch`) is not needed on the G2.
- Breaks (safety, not function): nothing refuses a Node image (110E, 7 partitions) on a G2 board or a G2 image on a Node in Loader mode. Today the layout-differs case logs both strings and **the image wins** (VERSION.txt 0.5.1 entry, `FirmwareJob.cpp:1120`): a Node update.img selected by mistake would write a 3M `boot` at 0xF0000 of the G2 and leave the rest of the 12M boot stale, i.e. an unbootable board with no documented MASKROM recovery (row 42). If the VM builds both boards in one checkout, `output/image/update.img` is whichever was built last (row 23).
- Change: the profile carries the accepted chip tags; `SFI` tag != profile tag -> refuse before `EXF`; a layout mismatch between env.img and the board -> refuse (new `--force-layout` / a dialog to override), no longer "image wins"; show tag + git describe in the Source line.
- First-board test: `su-fw partitions --image <G2 update.img>` -> "Chip Tag:1106" (confirm the exact SFI text), six rows (env, idblock, uboot, meta, boot 12 MiB, userdata), no rootfs, boot.img 8-10 MiB fits.

### D3. Six partitions, the rootfs inside a 12 MiB `boot`, userdata = mtdblock5 (rows 9-16)

- Already works: the mtdparts parser handles `sfc_nor:`, `@offset`, K/M suffixes (`RockchipTool.cpp:472-540`), so the G2 string parses; `mtdPartsFromEnvImage` reads the same 64 KiB env.img format (row 18); a named partition absent from the layout is refused ("%1 is not in the board's partition layout", `FirmwareJob.cpp:1093`, `FleetFlasher.cpp:1241`); an image larger than its partition disables the row, which also guards an idblock over 256K (row 14); `userdata` (jffs2) is written with the size in sectors as before; the protected list idblock/uboot/env/meta is still the right one; a Node and a G2 in one fleet run get "differing flash layout" skips by design (one plan layout per run, `FleetFlasher.cpp:63-70,2708`).
- Breaks: the habit and the examples. `--partitions rootfs` (the 0.7.0 release note's daily case, `FirmwareCli.cpp:275` example string = the Node's layout) is refused on the G2; the daily partition is **`boot`** (sector 0x780, 0x6000 sectors), 8-10 MiB instead of the Node's 5 MiB rootfs, so one board takes longer than the Node's ~35 s (unmeasured). `--all-boards` skips a board whose `/proc/cmdline` has no mtdparts: the G2 is expected to carry it (same thunderboot/env.img design as the Node, row 17), but the SPL-side merge of `sys_bootargs` is not evidenced in the repo, so this is the first thing to read.
- Change: per-profile default partition set (G2: boot; Node: rootfs) for the tab's checkboxes and the `--help` examples; the status line names the layout's source; in a fleet, allow one plan per profile (mixed benches) or keep refusing and say so (decide in 0.8.0 scoping).
- First-board test (read-only): `adb shell cat /proc/cmdline` -> expect `mtdparts=sfc_nor:64K(env),256K@64K(idblock),256K(uboot),384K(meta),12M(boot),3M(userdata)` and `root=/dev/rd0 rootfstype=erofs`; `su-fw status` prints that layout; `adb shell ls -l /dev/block/by-name/` -> boot -> mtdblock4, userdata -> mtdblock5; `su-fw flash-soc --serial <G2> --partitions boot --dry-run`. First write (one partition): `userdata` (3 MiB empty jffs2: nothing of value, validates the jffs2 size handling) and then `boot` with **the same build the board already runs**; never idblock/uboot/env/meta on the first board until the MASKROM route is known (row 42).

### D4. ADB gadget: same VID/PID, new product string, a serial string written by the script (rows 29-30)

- Already works: `isAdbGadget()` (0x2207/0x0006); `adb -s <serial>` selection; `--all-boards` counts 0x2207:0006 gadgets against `adb devices` (`FleetFlasher.cpp:1109`).
- Risk: the learned-port mapping assumes the gadget has **no** USB serial string, so that the ADB device and the Loader device share the bus-address suffix (`UsbProbe.h:21-26`, measured on the Node 2026-10-14). The G2 script writes an iSerialNumber (`post.sh:164-165`) exactly as the Node script does (`BG2 post.sh:129-130`), so the G2 is expected to look like the Node, but the Node's behaviour is itself unexplained (open question 5). If Windows does expose the G2's serial, `portKey()` returns `locationPath` for the ADB device and the bus address for the Loader device (empty iSerial, row 32); the mapping then sees "a Loader device on another port or nobody's" and stops before any byte is written: safe, but the fleet flash would be unusable on the G2.
- Change: key the port on the Windows location path (`SPDRP` location paths, `UsbProbe.cpp:71,119`) for every device and fall back to the bus-address suffix; record whether a board's gadget carries a serial string in the inventory; use the gadget's product string ("rv1106g-stacked-gc2083" / "rv1106bg2-gc2083") as the cheapest profile auto-detection on the host (Linux sysfs `product` is already read, `UsbProbe.cpp:171`; Windows needs the bus-reported device description).
- First-board test (read-only): Device Manager > the G2's ADB device > Details > "Device instance path" (serial or `6&...`); `adb devices`; `adb shell cat /proc/cpuinfo | grep Serial`; `adb shell cat /sys/kernel/config/usb_gadget/rockchip/strings/0x409/serialnumber`; do the same for a Node on the same hub port. Note a `Serial: 0000000000000000` would be used as-is by the script (the fallback only triggers on an empty line).

### D5. No documented MASKROM entry on the stacked board; BootROM PID unknown (rows 33, 42)

- Already works: the MASKROM flow (`LD` -> `Mode=Maskrom` -> `UF`) is generic and should pass the chip check on the G2 (D2). A blank first board can only be flashed this way (BootROM USB download when no idblock is found: general Rockchip behaviour, not evidenced in the repo).
- Breaks: the tab's "hold MASKROM and replug" instruction (`SocFlasher.h:33`) has no button on the G2; the recovery after a bad idblock/uboot/env write is undefined; a failed rockusb falls back to `rbrom` **without** the PHY restore BG2 added for the RV1103B (row 38), and on the rig the BootROM download never enumerated after a soft reset (`rockusb.config:7-8`), so the G2's rbrom fallback may be a dead end too.
- Change: profile field `maskromEntry` ("button" / "unknown") driving the hint text; refuse writes to idblock/uboot/env/meta on a profile whose MASKROM entry is unknown unless explicitly overridden; later, optionally, a "Ctrl+B at 1.5 Mbaud during boot" helper for boards with the console wired (row 41) once the BootROM is known to enumerate.
- First-board test: none that writes. Ask Moses for the MASKROM method (Core/Carrier schematic: pad, NOR CS/CLK short) before any loader-partition write.

### D6. CC1310 path through the SoC (rows 43-47)

- Already works: the bridge (`rfmcu bridge`, 127.0.0.1:7000, `/dev/ttyS1`, `McuLink.cpp:397`), the `command -v rfmcu` probe (rfmcu is symlinked into /usr/bin, row 45), `killall rfmcu` for a stale bridge (`McuLink.cpp:19-21`; rfmcud is a different process name and yields by flock), `mcu-info` (HELLO / CLI `version`, `power`: read-only), role selection.
- Risk: `mcu-update` and `mcu-set-role` send the CLI command `bootloader` so the CC1310 reboots into its bootloader (`McuUpdater.h:41-48`), and the application restarts after END/COMPLETE. On the stacked board a CC1310 reset drops SOC_PWR_EN (row 44) unless the bootloader is the 14 Oct 2026 build with `BOOTLOADER_SOC_PWR_EN`. With an older bootloader the SoC and the bridge die mid-update ("the connection to the rfmcu bridge on board %1 was closed", `McuLink.cpp:366`), the CC1310 may be left in its bootloader and, on battery, the node is off. Whether the running application keeps DIO8 high across its own restart is a CC1310-firmware fact not in this repo.
- Change: profile flag `cc1310ResetCutsSocPower`; on such a profile, require a bootloader/firmware version known to hold SOC_PWR_EN (ask the CLI `version` first, compare with a minimum from the profile) or an explicit `--confirm-soc-power`; say it in the log and the `mcu-update --help`.
- First-board test: `su-fw status --mcu` and `su-fw mcu-info` only; the first `mcu-update` through the SoC only after Moses confirms the bootloader on the carrier's CC1310 (open question 3), on USB power, with the J-Link / direct-UART route ready. Also check that the stacked rfmcu answers the `status` command su-fw prints after a fleet reset (the fork predates BG2's latest rfmcu, row 46; `status` itself was not checked).

### D7. `adb reboot loader` versus the CC1310 power latch (rows 40, 44)

- Already works: the tool's sequence (`adb reboot loader`, poll `LD` 30 s, "board did not enter MASKROM/Loader within 30 s", `SocFlasher.h:37-39`) is the right one and writes nothing on failure.
- Risk: rcK tells the CC1310 "soc alive 0 down" before the reboot; if the CC1310 answers by releasing SOC_PWR_EN, the SoC never reaches U-Boot (on battery the latch drops). Not visible in the repo.
- Change: profile-specific hint when the 30 s wait fails ("on the stacked board the CC1310 may have cut the SoC's power: power-cycle, then retry"); optional longer wait per profile.
- First-board test: USB-powered, battery state as Moses prefers; `adb reboot loader`; watch `LD` and the Device Manager for 30 s; power-cycle if nothing appears.

### D8. Image source on the VM (rows 20, 23)

- Already works: the SSH pull (`output/image/update.img`, RKFW magic check, git describe, size, time); the SFI summary shows the tag.
- Risk: same path for both boards if the VM builds both in one checkout; the tag (1106 vs 110E) and the partition count are the only tell-tales until D2's refusal exists.
- Change: one SSH profile / remote folder per board profile; D2's refusal.
- First-board test: pull, read the summary: tag 1106, six entries plus the bootloader; size roughly 12-14 MB (env 64K + idblock + uboot + meta 384K + boot 8-10 MiB + userdata 3M + download.bin; expected, not measured).

### D9. Serial console (row 48)

- Already works: 1500000 baud is in the baud list and the auto-baud candidates; the Firmware tab's "reboot loader via a connected serial tab" works on a respawn shell; the "Node" quick-command group applies as is.
- Risk: which connector or pads carry UART2_M1 on the assembled node is not stated; `loglevel=0` means a quiet console.
- Change: none.

### D10. Timing and verify (rows 10, 13)

- A G2 `boot` write moves 8-10 MiB (the Node's rootfs: 5 MiB); verify-after-write with `RL` would read it back once more. Expect the per-board time and the fleet's `--max-parallel` sweet spot to shift; measure on the first board before quoting numbers.

Same shape as the 0.5 plan (`docs/firmware-update/PLAN.md:106-119`: headers first, packages in their own `build/wf-<pkg>` directories, two at a time, then integration, review, fixes, docs, the real-board run). Effort figures are rough estimates in agent-hours of implementation plus tests, not measurements; models follow the house policy (Sonnet for mechanical work, Opus where rules are designed, Fable for the review).

|---|---|---|---|---|
